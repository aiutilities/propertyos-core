## 1. Purpose

PropertyOS exists to create an open, extensible and intelligent operating foundation for properties, workspaces and hospitality environments.

It helps organizations manage and automate the complete lifecycle of managed spaces without forcing every organization into the same rigid operating model.

PropertyOS provides shared infrastructure for people, spaces, facilities, assets, maintenance, reservations, procurement, inventory, documents, workflows, communication, automation and artificial intelligence.

## 6. Product Philosophy

Software should adapt to organizations.

Organizations should not be forced to distort their operations around inflexible software.

PropertyOS therefore provides stable shared foundations while allowing operating models, workflows, interfaces and specialized capabilities to evolve independently.

The platform must remain useful to a small property operator while being architecturally capable of supporting larger organizations and ecosystems.

## 8. Architectural Principles

### Stable core, innovative edges

The core should provide durable platform contracts.

Specialized innovation should happen through plugins, integrations, themes, workflows and AI specialists wherever practical.

### Clear boundaries

Modules must have explicit responsibilities.

Business logic must not be hidden inside presentation code.

Infrastructure concerns must not silently control domain decisions.

### API-first behaviour

Important capabilities should be accessible through stable APIs.

The API is a first-class product, not an implementation detail.

### Event-driven collaboration

Modules should communicate through explicit contracts and events where asynchronous collaboration is appropriate.

Hidden coupling should be avoided.

### Replaceability

Platform components should remain replaceable whenever practical.

Organizations must not be trapped by unnecessary proprietary dependencies.

### Deterministic foundations

Correctness-sensitive business operations must remain deterministic.

AI may advise, classify, summarize, recommend and orchestrate, but it must not silently weaken deterministic controls.

### Operational readiness

Health, metrics, monitoring, backup, restore and controlled upgrades are product capabilities—not deployment afterthoughts.

---

## 9. AI Principles

PropertyOS is AI-native, but AI must remain accountable.

### AI should reduce effort

AI should remove repetitive work, surface relevant information and help people make better decisions.

### AI should preserve control

Users and organizations must retain authority over consequential actions.

### AI should be reviewable

AI recommendations and decisions should expose reasons, confidence, evidence or relevant context whenever practical.

### AI should respect policy

Permissions, workflow rules, security policies and deterministic constraints apply equally to AI-triggered actions.

### AI should be provider-agnostic

PropertyOS should avoid permanent dependence on a single model or provider.

### AI should fail safely

Provider errors, unavailable models or uncertain responses must not compromise core operations.

### AI should augment responsibility

AI may assist people. It must not erase accountability.

---

## 10. Plugin Principles

Everything that can reasonably live outside the stable core should be considered for plugin implementation.

The plugin platform must support installation, validation, dependency management, activation, deactivation, upgrade, rollback, uninstall, permissions, publication governance, trusted publishers and runtime containment.

Core stability must not be sacrificed for extension convenience.

Plugins must use declared contracts rather than undocumented internal dependencies.

---

## 11. Theme Principles

Themes control presentation.

Plugins control behaviour.

Themes must not contain hidden business logic.

A theme should be replaceable without changing domain data or operational rules.

Accessibility, usability and responsive behaviour are part of theme quality.

---

## 12. API Principles

PropertyOS APIs should be:

- explicit
- versioned
- documented
- permission-aware
- predictable
- testable
- observable
- backward compatible whenever practical

Breaking changes require deliberate governance and clear migration guidance.

---

## 13. Workflow and Automation Principles

Automation should make operations more reliable, not more mysterious.

Workflows must have explicit triggers, understandable states, visible transitions, controlled permissions, auditable outcomes and safe failure behaviour.

Manual overrides should be available where operational responsibility requires them.

---

## 14. Security Principles

Security is a platform responsibility.

PropertyOS must favour:

- least privilege
- explicit authorization
- secure defaults
- auditable actions
- trusted package verification
- controlled migrations
- secret isolation
- fail-closed readiness
- responsible vulnerability disclosure
- timely security maintenance

Security controls must not be bypassed for development convenience in release builds.

---

## 15. Data Principles

Organizations should control their operational data.

PropertyOS should favour:

- open and documented schemas
- exportability
- migration transparency
- clear ownership
- integrity constraints
- traceable changes
- practical portability
- responsible retention
- privacy by design

Data lock-in must never become a business strategy.

---

## 16. Documentation Principles

Documentation is part of the product.

An undocumented capability is incomplete.

Documentation includes conceptual guides, API references, architecture decisions, examples, diagrams, operational runbooks, migration guidance, troubleshooting and release evidence.

Documentation should help newcomers begin quickly and help maintainers reason deeply.

Generated documentation must be distinguishable from authoritative human-governed documentation.

---

## 17. Testing and Release Principles

Every release must be evidence-based.

PropertyOS favours:

- automated tests
- integration tests
- regression tests
- reproducible builds
- migration preflight
- release certification
- operational validation
- documented evidence
- immutable published tags
- controlled release processes

Feature velocity must never override release integrity.

Certification precedes release.

Published history must be preserved.

---

## 18. Open-Source Principles

PropertyOS should grow through openness, transparency and shared stewardship.

The project must welcome responsible contribution, document contributor expectations, explain governance decisions, preserve attribution and avoid artificial ecosystem lock-in.

Open source is not merely a distribution channel. It is part of the platform's identity.

## 19. Community Principles

## 23. Decision Test

Major decisions should be evaluated using these questions:

1. Does this strengthen or weaken organizational control?
2. Does this belong in the stable core or at the extensible edge?
3. Does this preserve security and accountability?
4. Does this increase unnecessary coupling?
5. Does this remain understandable to future maintainers?
6. Does this improve interoperability?
7. Does this preserve release integrity?
8. Does this align with the official PropertyOS identity?
9. Would the community reasonably trust this decision?
10. Does this move PropertyOS closer to its long-term vision?

A decision that materially conflicts with the Constitution must be reconsidered or accompanied by a formal constitutional amendment.
