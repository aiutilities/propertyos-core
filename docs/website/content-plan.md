# PropertyOS Website Content Plan

This document defines the content required for the future public PropertyOS
website.

It does not implement a website or modify the PropertyOS product frontend.

---

## 1. Content Objectives

Website content should help visitors:

- understand PropertyOS quickly;
- identify whether it fits their needs;
- verify current product status;
- find installation guidance;
- find developer documentation;
- understand the extension ecosystem;
- access release evidence;
- understand governance;
- join the community;
- report security issues correctly.

Content must distinguish released capabilities from future plans.

---

## 2. Editorial Principles

Website content should be:

- accurate;
- concise;
- evidence-based;
- accessible;
- technically credible;
- consistent with repository governance;
- clear about version scope;
- transparent about limitations;
- free of unsupported claims;
- easy to maintain.

Marketing language must not contradict certified product evidence.

---

## 3. Official Positioning

The primary positioning is:

PropertyOS — The Open Source AI-Native Operating System for Properties,
Workspaces and Hospitality.

The primary vision statement is:

Build infrastructure for the physical world.

The website should consistently identify Cogzidel Technologies Pvt. Ltd. as
the creator, maintainer and steward of PropertyOS.

---

## 4. Home Page Content

The Home page should include:

- official positioning;
- vision statement;
- concise product explanation;
- major capability groups;
- architecture principles;
- AI-native platform explanation;
- plugin and theme ecosystem;
- current stable release;
- open-source licence;
- primary calls to action.

Suggested calls to action:

- Explore the platform;
- Read the documentation;
- View the source;
- Download the release;
- Join the community.

The Home page must not claim unavailable hosted services or active
marketplaces.

---

## 5. Product Overview Content

The Product Overview should explain:

- what PropertyOS is;
- what operational problems it addresses;
- who can deploy it;
- how modules work together;
- how plugins extend capability;
- how themes customize presentation;
- how AI integrates with governed operations;
- how self-hosting works;
- how governance protects the platform;
- what is included in the current release.

Product content should link to release certification where appropriate.

---

## 6. Core Platform Content

The Core Platform page should explain:

- identity;
- authentication;
- authorization;
- properties;
- tenants;
- leases;
- rent;
- payments;
- workflows;
- events;
- notifications;
- scheduling;
- storage;
- search;
- documents;
- configuration;
- health and metrics.

The page should describe certified capabilities without exposing internal
implementation details unnecessarily.

---

## 7. Operations Content

Operations content should explain:

- maintenance;
- facilities;
- assets;
- staff;
- vehicles;
- access control;
- reservations;
- helpdesk;
- procurement;
- inventory;
- reporting.

Each capability page should identify whether the feature belongs to the current
certified release.

---

## 8. Developer Content

Developer content should organize:

- getting started;
- repository structure;
- local development;
- architecture;
- APIs;
- events;
- SDKs;
- plugins;
- themes;
- AI development;
- testing;
- contribution;
- release compatibility.

Canonical developer content should remain linked to `DEVELOPER_PORTAL.md` and
`docs/developer/`.

---

## 9. Ecosystem Content

Ecosystem content should explain:

- plugins;
- themes;
- AI providers;
- AI specialists;
- certification;
- compatibility;
- publisher requirements;
- security review;
- future marketplace plans.

Planned marketplaces must be labelled clearly as future work until operational.

---

## 10. Documentation Content

Documentation content should route visitors to:

- installation;
- configuration;
- administration;
- deployment;
- troubleshooting;
- generated module documentation;
- developer guides;
- governance;
- release evidence;
- upgrade guidance.

Documentation pages should identify version scope and canonical source.

---

## 11. Downloads Content

The Downloads section should provide:

- current stable release;
- source archives;
- release notes;
- release manifest;
- checksums;
- installation guidance;
- upgrade guidance;
- compatibility information;
- known limitations.

Every downloadable artifact should be traceable to an official release.

---

## 12. Release Content

Release pages should explain:

- release status;
- release date;
- source commit;
- tag;
- notable changes;
- migration impact;
- compatibility;
- certification;
- known limitations;
- support expectations.

Release content must align with `CHANGELOG.md` and
`RELEASE_GOVERNANCE.md`.

---

## 13. Community Content

Community content should include:

- contribution guidance;
- GitHub Discussions;
- GitHub Issues;
- Code of Conduct;
- support routes;
- roadmap participation;
- architecture discussions;
- plugin discussions;
- theme discussions;
- AI discussions.

Security vulnerabilities must not be routed to public community channels.

---

## 14. Governance Content

Governance content should link directly to:

- Constitution;
- Manifesto;
- Governance;
- Maintainers;
- Contribution Guide;
- Code of Conduct;
- Security Policy;
- Support Policy;
- Release Governance;
- Plugin Marketplace Governance;
- Theme Marketplace Governance;
- AI Ecosystem Governance;
- Trademark Policy;
- Roadmap;
- Changelog.

Governance content must remain accessible without registration.

---

## 15. Security and Support Content

Security content should explain:

- private vulnerability reporting;
- supported versions;
- coordinated disclosure;
- deployment responsibilities;
- security limitations.

Support content should distinguish:

- community support;
- bug reports;
- feature requests;
- documentation questions;
- security reporting;
- commercial support where separately offered.

These pages must align with `SECURITY.md` and `SUPPORT.md`.

---

## 16. Roadmap Content

The Roadmap page should summarize:

- completed work;
- work in progress;
- near-term priorities;
- mid-term priorities;
- long-term direction;
- ecosystem plans.

The page must state that roadmap items are directional and not guaranteed
release commitments.

---

## 17. Visual Content

Visual content may include:

- product screenshots;
- architecture diagrams;
- module maps;
- deployment diagrams;
- extension ecosystem diagrams;
- release-certification summaries.

Visuals must:

- reflect actual product behaviour;
- avoid exposing private data;
- include meaningful alternative text;
- identify the applicable version;
- avoid implying unavailable functionality.

---

## 18. Showcase Content

A future Showcase section may feature:

- real deployments;
- approved case studies;
- community plugins;
- community themes;
- integrations;
- implementation stories.

A showcase entry must have permission from the relevant operator or publisher.

Unverified claims must not be presented as official adoption evidence.

---

## 19. Blog and Announcements

A future Blog or Announcements section may publish:

- release announcements;
- governance updates;
- technical articles;
- ecosystem updates;
- community highlights;
- security advisories where appropriate.

Announcements must distinguish:

- released;
- planned;
- experimental;
- deprecated;
- withdrawn.

Security disclosures must follow coordinated-disclosure requirements.

---

## 20. Content Review

Website content should be reviewed for:

- factual accuracy;
- release alignment;
- compatibility;
- governance consistency;
- security;
- privacy;
- accessibility;
- trademark usage;
- broken references;
- outdated claims.

Material product claims should be supported by current release evidence.

---

## 21. Content Sources

Website content should be derived from canonical repository sources.

Primary sources include:

- `README.md`;
- `DEVELOPER_PORTAL.md`;
- `ROADMAP.md`;
- `CHANGELOG.md`;
- governance documents;
- architecture documents;
- generated module documentation;
- release notes;
- release manifests;
- certification records.

Website copy must not override canonical repository documents.

---

## 22. Content Maintenance

Content maintenance should include:

- version review;
- release review;
- broken-link review;
- ownership review;
- security review;
- trademark review;
- outdated-content removal;
- archival of historical material.

Changes should remain attributable through repository history.

---

## 23. Product-Freeze Boundary

During Repository Foundation:

- no website runtime is implemented;
- no product frontend is modified;
- no backend service is modified;
- no public domain is configured;
- no analytics service is enabled;
- no hosted marketplace is activated;
- no release artifact is republished.

This document defines content only.
